### Нефункциональные требования

| №  | Требование                                                                                                                             |
|:------:|--------------------------------------------------------------------------------------------------------------------------------------------|
| NFR-01 | Время получения скоринга для новой заявки (с сайта) не должно превышать 5 секунд.                                                          |
| NFR-02 | Доступность сервисов (Credit API, Сайт, Интернет-банк) должна составлять 99.9% (24/7).                                                     |
| NFR-03 | Критически важные компоненты должны горизонтально масштабироваться.                                                                        |
| NFR-04 | АБС не должна испытывать прямую нагрузку от онлайн-заявок (никаких прямых запросов к БД АБС).                                              |
| NFR-05 | Передача заявок в Кредитный конвейер должна быть асинхронной, чтобы не блокировать ответ клиенту.                                          |
| NFR-06 | Весь трафик между клиентом и серверами должен шифроваться (TLS 1.2+).                                                                      |
| NFR-07 | Все действия с заявками должны логироваться для аудита (кто, когда, что изменил).                                                          |
| NFR-08 | Новые компоненты должны использовать технологии, уже имеющиеся в банке (Java, Python, PostgreSQL) или совместимые с ними.                  |
| NFR-09 | Система скоринга не должна перегружаться дополнительными предрасчетами (предодобренные предложения рассчитываются не чаще 1 раза в сутки). |
| NFR-10 | Заявки должны обрабатываться в порядке очереди, без потерь при сбоях (durable queue).                                                      |

### Решение

#### Логика принятия решений и выбор технологий

При разработке решения мы руководствовались следующими принципами:
1. Разгрузка АБС – запрет на прямые запросы к АБС из онлайн-каналов (NFR-04). Это обеспечивается введением отдельного микросервиса Credit API и асинхронной очередью.
2. Сохранение отзывчивости – клиент должен получить ответ мгновенно, даже если заявка будет обрабатываться минуты (NFR-01). Достигается паттерном "асинхронная заявка с немедленным подтверждением".
3. Масштабируемость – выбор технологий, поддерживающих горизонтальное масштабирование (Spring Boot, Kafka, PostgreSQL с репликацией).
4. Использование существующей экспертизы – в банке есть специалисты по Java, Python, PostgreSQL. Kafka выбрана как перспективная технология, на которую можно постепенно мигрировать (PoC).
5. Соответствие стратегии Strangler Fig – новые функции выносятся в отдельные микросервисы, что позволяет постепенно замещать монолит.


---

### Обоснование архитектурных решений

Выбранное решение с выделением Credit Application API и использованием Kafka является оптимальным, так как:

1. Полностью удовлетворяет нефункциональным требованиям (разгрузка АБС, масштабируемость, асинхронность)
2. Соответствует стратегическому направлению (микросервисная архитектура)
3. Минимизирует риски за счёт использования проверенных паттернов (Saga, outbox, BFF)
4. Учитывает существующую экспертизу банка (Java, Python, PostgreSQL)
5. Создаёт основу для дальнейшей цифровой трансформации
