### Функциональные требования

| № | Действующие лица или системы | Use Case | Описание |
|:-----:|:---------------------------------|:------------|:-------------|
| UC-01 | Новый клиент / Сайт | Просмотр списка депозитов | Посетитель сайта видит список доступных депозитов с актуальными ставками, получаемыми из АБС (через промежуточный слой) |
| UC-02 | Новый клиент / Сайт | Подача заявки на депозит | Клиент заполняет ФИО и телефон. Заявка сохраняется, менеджер кол-центра получает уведомление |
| UC-03 | Существующий клиент / Интернет-банк | Просмотр персонализированных ставок | Клиент видит базовые и персональные ставки, рассчитанные на основе его истории и текущих рисков |
| UC-04 | Существующий клиент / Интернет-банк | Подача заявки на депозит | Клиент выбирает счёт, сумму, подтверждает СМС-кодом. Заявка отправляется в обработку |
| UC-05 | Менеджер кол-центра / Система кол-центра | Обработка заявки с сайта | Менеджер видит заявку, может предложить особые условия, связывается с клиентом |
| UC-06 | Менеджер бэк-офиса / АБС | Подтверждение депозита | Менеджер проверяет заявку, подтверждает условия. После подтверждения клиенту отправляется СМС |
| UC-07 | Система / СМС-шлюз | Отправка уведомлений | Отправка СМС о подтверждении ставки и открытии депозита |
| UC-08 | Менеджер бэк-офиса депозитов / АБС | Управление ставками | Внесение актуальных ставок в АБС (замена Excel-файлов) |

### Нефункциональные требования

| № | Требование |
|:-----:|:---------------|
| NFR-01 | Доступность интернет-банка и сайта – 99.9% (24/7). В случае сбоя в ЦОД автоматическое переключение на резервный ЦОД |
| NFR-02 | Время отклика интерфейсов (загрузка страниц, отображение ставок) – не более 300 мс |
| NFR-03 | Время обработки заявки (от подтверждения клиентом до отправки в бэк-офис) – не более 2 секунд |
| NFR-04 | Шифрование трафика (TLS 1.2+) для всех внешних каналов (сайт, интернет-банк) |
| NFR-05 | Отсутствие прямой нагрузки на БД АБС со стороны онлайн-каналов (АБС перегружена и масштабируется только вертикально) |
| NFR-06 | Использование существующих технологий (MS SQL, Oracle, Java, Python) для новых компонентов |
| NFR-07 | Совместимость новых компонентов с платформами разработки, существующими в банке |
| NFR-08 | Асинхронное взаимодействие между интернет-банком и АБС для снижения связанности и нагрузки |
| NFR-09 | Возможность горизонтального масштабирования новых микросервисов |
| NFR-10 | Логирование всех операций для аудита и мониторинга |
| NFR-11 | Защита персональных данных в соответствии с 152-ФЗ |
| NFR-12 | Документирование API новых сервисов для дальнейшего расширения |
| NFR-13 | Минимизация доработок ядра АБС и системы кол-центра силами подрядчика |

### Решение

#### Диаграмма контекста (C4 Level 1)

[Диаграмма контекста:](context-diagram.puml)

Описание контекста:
Система открытия депозитов взаимодействует с четырьмя типами пользователей:
- Клиенты банка (новые и существующие) через сайт и интернет-банк
- Менеджеры кол-центра, обрабатывающие заявки с сайта
- Менеджеры бэк-офиса, подтверждающие депозиты и управляющие ставками
- Менеджеры фронт-офиса (для случаев, когда клиент приходит в отделение)

Внешние системы:
- СМС-шлюз для отправки уведомлений
- АБС для учёта депозитов и хранения ставок
- Система кол-центра для работы с заявками

#### Диаграмма контейнеров (C4 Level 2)

[Диаграмма контейнеров](container-diagram.puml)

Детализация компонентов:

| Контейнер | Технологии | Описание |
|:----------|:-----------|:---------|
| Сайт | PHP, React.js | Существующий сайт, дорабатывается для отображения депозитов и сбора заявок |
| Интернет-банк (существующий) | ASP.NET MVC, MS SQL | Монолит, требует минимальных доработок (только интерфейсы) |
| API Gateway | .NET Core / Java | Новый компонент, единая точка входа. Реализует маршрутизацию, аутентификацию, rate limiting |
| Сервис депозитов (новый) | Java / Spring Boot, PostgreSQL | Микросервис для управления заявками. Реализует бизнес-логику, взаимодействует с АБС асинхронно |
| Message Broker | Apache Kafka | Обеспечивает асинхронное взаимодействие между интернет-банком и АБС |
| Сервис СМС (новый) | Java / Spring Boot | Микросервис для отправки СМС (изолирует функционал от ядра интернет-банка) |
| АБС (существующая) | Delphi, Oracle | Модифицируется: добавляются таблицы для ставок и заявок, Kafka-клиент |
| Система кол-центра | React, Java, PostgreSQL | Дорабатывается для отображения заявок с сайта |

---
#### Обоснование архитектурных решений

1. Выделение нового микросервиса депозитов
    - Следует принципу единой ответственности
    - Позволяет горизонтально масштабировать наиболее нагруженную часть
    - Использует Java (есть экспертиза в команде АБС)

2. Использование Kafka для асинхронного обмена
    - Разгружает АБС (нет прямых синхронных вызовов)
    - Обеспечивает гарантированную доставку заявок
    - Позволяет легко добавлять новых потребителей в будущем
    - *Компромисс:* текущая версия интернет-банка несовместима с Kafka, поэтому взаимодействие организовано через новый микросервис

3. Выделение сервиса СМС
    - Избегает доработок ядра интернет-банка силами подрядчика
    - Может использоваться всеми каналами
    - Реализуется силами команды банка на знакомом стеке

4. API Gateway
    - Единая точка входа упрощает обеспечение безопасности (TLS)
    - Позволяет реализовать rate limiting для защиты АБС
    - Облегчает будущий переход на микросервисную архитектуру

5. Доработка АБС вместо Excel
    - Ставки становятся доступны всем системам в реальном времени
    - Автоматизируется расчёт персонализированных ставок
    - Сохраняется целостность данных и контроль доступа

### Альтернативы

| Альтернатива | Описание | Причина отклонения |
|:-------------|:---------|:-------------------|
| Прямая интеграция интернет-банка с АБС | Интернет-банк напрямую вызывает API АБС | Отвергнуто из-за перегруженности АБС и невозможности горизонтального масштабирования |
| Реализация всей логики в интернет-банке | Расширение монолита интернет-банка | Увеличивает связанность, требует доработок от подрядчика, не решает проблему нагрузки на АБС |
| Использование RabbitMQ вместо Kafka | Более простая очередь сообщений | Kafka выбрана как стратегическая платформа для будущих событийно-ориентированных архитектур |
| Хранение ставок в отдельной БД | Вынос ставок из АБС | Требует синхронизации, усложняет управление, противоречит желанию использовать существующие технологии |

### Недостатки, ограничения, риски

| Риск | Вероятность | Влияние | Меры митигации |
|:-----|:-----------:|:-------:|:---------------|
| Перегрузка АБС при росте числа заявок | Средняя | Высокое | Kafka-буферизация, rate limiting, горизонтальное масштабирование микросервисов |
| Сложность синхронизации ставок между АБС и новыми сервисами | Средняя | Среднее | Проектирование чёткого API, использование событий при изменении |
| Недостаточная экспертиза команды в Kafka | Высокая | Среднее | Обучение, привлечение консультанта на начальном этапе |
| Задержки при доработке АБС | Высокая | Высокое | Параллельная разработка, чёткое API-контрактирование |
| Несоответствие целевым показателям доступности (99.9%) | Средняя | Высокое | Резервный ЦОД, автоматическое переключение, мониторинг |
| Риск потери заявок при сбоях Kafka | Низкая | Критическое | Настройка персистентности, репликация, мониторинг dead-letter queues |

#### Ограничения решения

1. На этапе MVP бэк-офис участвует в обработке, что не позволяет достичь полностью автоматического открытия
2. Скорость обработки заявок зависит от производительности АБС (вертикальное масштабирование ограничено)
3. Требуется миграция данных о ставках из Excel в АБС (организационные усилия)
4. Новые микросервисы увеличивают сложность инфраструктуры и требуют дополнительных ресурсов DevOps
